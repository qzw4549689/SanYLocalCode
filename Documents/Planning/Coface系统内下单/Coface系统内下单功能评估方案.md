# Coface 系统内下单功能评估方案

> **版本**：V1.0（评估稿，待业务确认）
> **日期**：2026-07-23
> **状态**：⏸️ 待业务确认后进入开发
> **配套文件**：`Coface系统内下单功能评估方案.xlsx`（同目录，供业务确认用）

---

## 1. 背景

原 PRD 设计：Coface Report（商业报告）与 URBA360 监控的**下单动作由业务人员在 Coface 平台线下人工完成**，D365 系统只负责查询已有订单并拉取报告数据。

现业务提出新需求：**将下单动作改为在 D365 系统内完成**，初步设想放在「关联客户代码」（绑定 Coface ID）阶段，通过按钮触发。

本文档为技术评估与整体方案，供业务确认。

---

## 2. 现状（事实）

### 2.1 当前流程

```
【发起信用评估】→【关联客户代码】（绑定 Coface ID，弹窗搜索企业并绑定）
  →【内外部数据集成】（系统自动触发 Coface 数据同步）
       ① 查询 URBA360 监控订单
       ② 查询 Report 订单（按国家配置匹配产品）
       ③ 取 URBA360 内容 + Report JSON/PDF
       ④ 写入客户信用标签、保存 PDF 附件
```

### 2.2 关键事实

| 项目 | 现状 |
|---|---|
| 下单调用 | **代码中不存在任何下单调用**（无 POST 下单接口），全部依赖线下人工下单 |
| 系统取数 | 只有 GET 查询已有订单 + 取内容 |
| 无订单时行为 | **不报错、不阻断**：评级类指标填 "O"、数值指标填 null，`mcs_api_msg` 记"未下单"警告，整体仍写 SUCCESS → 信用分基于残缺数据计算。⚠️ **与 PRD 不符**：PRD 要求"订单不存在或还在准备中，提醒业务等待订单完成后才能完成外部数据集成，流程停留在「关联客户代码」状态"（见 2.5 节） |
| 绑定 Coface ID | 在「发起信用评估」「关联客户代码」阶段可通过【搜索 Coface 企业】弹窗绑定，写回评估记录 + 客户主数据；进入「内外部数据集成」前强制校验 Coface ID 非空 |
| Report 产品选择 | 已配置化（`ms_systemconfiguration.CofaceCountryConfig`）：非受限国家 `customized-report/301`、受限 39 国 `full-report`、俄罗斯 `customized-report/21000`，**下单时可直接复用** |
| 可复用链路 | 【搜索 Coface 企业】= 按钮 → 弹窗/JS → Custom API → 后端 Plugin 调 Coface API，链路成熟可直接照搬 |

### 2.3 Coface 官方下单接口（文档已齐）

| 接口 | 方法 | 必填参数 | 说明 |
|---|---|---|---|
| 即时报告查询 | GET `/companies/reports` | externalId + countryCode | **有即时报告可直接用，无需付费下单** |
| URBA360 监控下单 | POST `/urba360/monitorings/orders` | externalId + countryCode（德国公司另需 legitimateInterest） | 返回 order id |
| 商业报告下单 | POST `/publications/orders` | externalId + countryCode + report/reportSlug | 返回 orderId + publicationId，状态 in-preparation |
| 未识别公司调查 | POST `/companies/identifications` | — | Coface 搜索不到的企业需先发起识别调查 |

### 2.4 关键约束（来自 Coface 接口文档）

| 约束 | 说明 |
|---|---|
| ⚠️ 下单限流 | 单用户 10-12 次/分钟，**每次下单前需间隔 5 秒** |
| ⚠️ 报告就绪时长 | 下单后 **6-7 个工作日**报告才就绪（in-preparation → Ready） |
| ⚠️ 双格式限制 | 有 39 个国家**不支持一个订单双格式**（HK/IN/JP/BR 等），JSON 和 PDF 需分别下单（注意：此列表与受限 39 国是两个不同列表） |
| ⚠️ 费用与幂等 | 下单即产生费用，接口**无幂等/去重机制**，重复提交 = 重复扣费 |

---

### 2.5 PRD 原文依据（阻断要求）

| 出处 | 原文 |
|---|---|
| PRD 方案概述第 6 条 | "在获取Coface数据集成前，会判断如果订单不存在或订单还在准备中，会提醒相关业务人员需等待相关客户的采购订单完成后，才能完成外部数据集成。" |
| PRD 状态流转规则 | "关联客户代码 > 如果已关联获取Coface ID并保存到客户表，允许点击【下一步】到3-内外部数据集成状态。如果Coface订单数据还未完成，会停留在本状态。" |
| PRD 数据集成环节说明 | "在本功能模块不会自动发起Coface订单商务采购，避免引起营销人员困惑或下单误操作。但会提供相关科法斯订单和数据准备状态查询，并提示给业务。" |
| PRD 接口设计说明 | "不支持通过本模块进行静默下单流程，因该部分涉及Coface对三一的计费等商务要求（开发阶段优先采用Coface线下下单预处理……从测试阶段发布需关闭掉任何相关下单代码）。" |

> **结论**：PRD 明确要求"无订单/订单未就绪 → 提醒 + 停留本状态"的阻断行为；PRD 禁止的是**静默自动下单**，本次改为按钮手动下单不与之冲突，但属于对 PRD 的需求变更，需业务确认。

## 3. 差距分析

| # | 差距 | 影响 |
|---|---|---|
| 1 | 系统无下单能力 | 走到「内外部数据集成」阶段才发现没订单时，流程无法自动闭环，需人工线下补单后重新触发 |
| 2 | 无订单时不阻断（**偏离 PRD**） | PRD 明确要求提醒并停留本状态（见 2.5 节）；当前缺失值兜底继续，信用分基于残缺数据计算，分数失真 |
| 3 | 下单时机晚（线下通常在发起评估后才人工下单） | 报告需 6-7 个工作日，流程整体被拉长 |
| 4 | 无订单状态跟踪字段 | 无法知道"是否已下单、是否已就绪"，无法防重复下单 |

## 4. 目标方案（推荐）

### 4.1 目标流程

```
【发起信用评估】
  →【关联客户代码】
       ① 通过【搜索 Coface 企业】绑定 Coface ID（现有功能，不变）
       ② 点击新增的【Coface 下单】按钮
           → 先查即时报告：有则直接标记“已就绪”，零费用
           → 再查已有有效订单：有则复用，不重复下单
           → 都没有才正式下单：URBA360 监控 + Report（两次调用间隔 5 秒）
           → 回写订单状态/订单号/下单时间到评估记录
  → 进入「内外部数据集成」前校验：订单“已就绪”才放行
       （是否允许人工强制放行，待业务确认）
  →【内外部数据集成】（现有逻辑不变，此时订单已就绪，直接取数）
```

**把下单提前到绑定阶段的核心价值**：报告需 6-7 个工作日才就绪，下单动作提前后，“等报告”与后续人工操作并行，避免走到「内外部数据集成」阶段才发现没报告、流程卡死。

### 4.2 下单决策逻辑（防重复扣费的核心）

```
点击【Coface 下单】
  ├─ ① 查即时报告（GET /companies/reports）
  │     └─ 有即时报告 → 标记"已就绪"，结束（不产生费用）
  ├─ ② 查已有有效订单（复用现有 GET 订单查询逻辑）
  │     └─ 有（含在途 in-preparation）→ 复用，更新状态，结束（不重复下单）
  └─ ③ 正式下单
        ├─ POST URBA360 监控订单
        ├─ 等待 5 秒（Coface 限流要求）
        └─ POST Report 订单（产品按现有国家配置自动选择；
            双格式 39 国按需 JSON/PDF 分两次下单）
```

### 4.3 防重复下单（三层防护，照搬厂端授信 BPP 成熟模式）

| 层级 | 措施 |
|---|---|
| 按钮层 | 仅「关联客户代码」阶段、已绑定 Coface ID 且未下单时可用 |
| JS 层 | 点击前实时查询服务端订单状态，已下单直接拦截提示 |
| 插件层 | 后端再次查询 Coface 已有订单，存在即复用，绝不重复 POST |

### 4.4 页面与字段

**新增按钮**：【Coface 下单】（命令栏按钮，与【搜索 Coface 企业】同区域）

**新增字段（评估记录表 `mcs_credit_record`）**：

| 字段 | 类型 | 用途 |
|---|---|---|
| Coface 下单状态 | 选项集 | 未下单 / 下单中 / 已下单待就绪 / 已就绪 / 下单失败 |
| Coface 下单信息 | 文本 | 订单号、publicationId、失败原因等详情 |
| Coface 下单时间 | 日期时间 | 防重 + 审计 |

**就绪确认方式**：报告 6-7 天才就绪，不做自动轮询，采用**按需刷新**——用户点击【进入下一阶段】时实时查询订单状态；如需自动更新，可后续加每日定时任务（二期可选）。

## 6. 关键业务影响与风险

| # | 事项 | 说明 | 建议 |
|---|---|---|---|
| 1 | **费用** | 下单即扣费，无幂等机制，重复下单 = 重复扣费 | 三层防重 + 先查即时报告/已有订单；504 家大客户已线下预处理，系统内下单仅针对"无有效订单的客户" |
| 2 | **等待时长不变** | 报告仍需 6-7 个工作日，系统内下单只是提前触发，不能消除等待 | 业务需接受评估流程在「关联客户代码」阶段停留数天；大客户提前批量下单的线下预处理建议保留作为补充 |
| 3 | **限流** | 两次下单间隔 5 秒，单次操作约 10-15 秒 | 单次按钮操作可接受；批量场景需排队（一期不支持批量） |
| 4 | **未识别公司** | Coface 搜索不到的企业需先发起识别调查，流程不同 | 建议一期不覆盖，仍走线下 |
| 5 | **双格式 39 国** | 部分国家 JSON/PDF 需分两次下单，可能产生两份费用 | 需业务确认是否接受 |
| 6 | **测试成本** | DEV/UAT 联调涉及真实下单接口 | 需先与 Coface 确认沙盒环境下单是否计费/有配额 |
| 7 | **PRD 历史背景** | PRD 明确"不支持静默下单、测试阶段发布需关闭任何下单代码"——针对的是**静默自动下单**；本次改为按钮手动下单属 PRD 需求变更 | 需业务书面确认本次变更；下单动作保留人工触发与完整审计字段 |
