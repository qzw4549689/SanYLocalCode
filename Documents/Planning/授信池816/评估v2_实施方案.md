## 二、实施方案（按模块）

### 1. 授信池主数据（A1）

- **不新建池实体**，厂端侧复用 `mcs_fca_quota`；信保侧新增 3 个汇总字段（建议挂 `mcs_fca_quota` 或客户主数据，与客户 1:1 口径保持一致）：
  - 信保官方限额 USD（插件实时汇总 `mcs_zxb_approvedquota` 有效记录）
  - 信保上浮限额 USD = min(官方 × 系数, 封顶)
  - 池总额/池余额（计算字段或查询时计算）
- **上浮配置**：按 816 最新要求（当前版本：批复限额 ×1.5、封顶 8M、部分国家不上浮）。国家清单待 816 明确；开发期间 816 可能修订，配置必须参数化（建议 `ms_systemconfiguration` JSON，同 CofaceCountryConfig 先例），系数/封顶/国家开关全部做成可改。
- **中信保取值依赖（重要边界）**：中信保授信模块由他人在 CRM 开发，限额/余额数据的维护不在我方范围。我方引擎只读其数据，**取值口径必须在开发前与对方对齐**（具体见 §三 P0-②），切忌按字段名想当然取值。
- 厂端额度调整+审批维持现状（`mcs_fca_quotaapp` + BPP，已上线），文档需写明"额度调整入口唯一在 CRM"。

### 2. 授信额度变动明细（A2）——复用 `mcs_fca_records` 扩展（v2.2）

**会议结论：不新建实体**，占用/释放明细记在现有台账表 `mcs_fca_records`；与现有字段语义不同的**一律新增字段**，不改已有字段含义。预期新增字段（最终以下一版 PRD 为准）：

| 新增字段建议 | 类型 | 说明 |
|---|---|---|
| credit_type | 选项集：FACTORY/SINOSURE | 区分厂端/中信保池（现有台账只有厂端） |
| biz_type | 选项集：OCCUPY（含重占）/RELEASE | 占用/释放方向（现有 adjust 字段语义不同，不动旧字段） |
| source_type / source_no | 选项集 + 文本 | DELIVERY/CANCEL/RETURN/SETTLE/REDCHARGE + 单据号 |
| related_source_id | 自关联 Lookup | 红冲溯源 |
| order_no / delivery_no | 文本 | 单据关联 |
| order_amount_A / return_amount_R / settle_amount_S | 货币 ×3 | 快照字段（若下版 PRD 保留） |
| amountCNY / fx_rate | 货币 + Decimal | 现有台账只有 USD 金额，CNY 与汇率快照按需新增 |

- **幂等**：`source_type + source_no + biz_type` 建唯一键（Alternate Key），插件查重，重复调用直接返回上次结果。
- **写入分工**：现有授予层插件（初始化/调整申请）写旧字段不变；占用/释放由新接口写入，新旧记录靠新字段区分，互不干扰。
- **金额口径**：现有台账为"调整前余额/调整金额/调整后余额（USD）"，与对方传参基本一致（v2.2 会议确认"金额字段基本与现在一致"）。

### 3. 占用/释放接收与保存（A3）——哑记账（v2.2）

**会议结论：金额由对方算好传入，我方不做 F=max(0,A−R−S) 计算**，职责只剩：校验入参 → 幂等保存台账 → 更新额度表余额 → 返回结果。

- 形态：**优先复用/轻量扩展 `mcs_AdjustFcaQuotaBalance`**（本来就是"调用方算好金额传入"的哑记账设计，与 v2.2 结论天然吻合；v2.1 的废弃定向撤回）。是否需要新参数（credit_type、source_type/source_no、幂等键、快照）等下一版 PRD 确定后评估——若改动大则按同模式新建 API，旧 API 保持不动。
- 处理逻辑（PreOp/事务内）：① 幂等检查；② 写 `mcs_fca_records`（新字段）；③ 更新 `mcs_fca_quota` 余额（厂端）/信保侧余额落点待下版 PRD；④ 失败整体回滚（插件天然同事务）。
- **我方不做的**：A/R/S 取数、F=max 公式、事件状态机——全在对方侧。

### 4. 额度校验 + 阻断/预警/特批（A4）

- 校验点：CRM 转销订单"待发货申请"环节（共识点 4 明确在 CRM）。
- 实现：校验插件/Custom API `mcs_CheckCreditBeforeDelivery`：判定订单授信类型 → 查对应池余额 → 三档（充足放行 / 预警放行+通知 / 阻断）。
- 特批：走既有 BPP 集成框架（同额度调整申请先例），特批通过后额度内放行并写明细备注。

### 5. 订单授信类型判定（A5）

- 规则：优先全额信保（信保上浮余额 ≥ 订单赊销金额）→ 不够则全额厂端 → 都不够进入阻断/特批。
- 实现：判定 API（输入客户+金额，返回 credit_type + 各池余额快照），上游在推交货单时调用并反写订单；发货后锁定（上游订单 `credit_locked`，不在我方）。
- 830 版本排除"池流转/已发货改投保"（群内确认 4），判定结果一经占用不可变，文档需写明。

### 6. 汇总计算与风险敞口（A6）

- 净占用 = ΣOCCUPY − ΣRELEASE（按 credit_type 分组），用 FetchXML 聚合，量大则落冗余字段+每日对账。
- **风险敞口口径拉通（决策点 3）**：两套公式并存（2026-08-20 已核实精确公式）：
  - **1641（已上 UAT，`mcs_CalcContractRiskExposure`，合同维度，合同评审时调用）**：A 类=合同签约占用+厂端已用余额+合同风险赊销−厂端授信额度−中信保有效限额**余额**汇总（T+1 动态余额、无上浮）；B 类=合同风险赊销−融资授信金额。
  - **816（客户维度汇总）**：交易风险敞口=客户签约占用+客户风险敞口(=厂端净占用)+信保净占用+合同风险赊销−客户授信池余额；池余额用批复限额**×1.5 上浮封顶 8M** 减自记净占用。另群内确认 3 还有第三种说法（订单维度发货敞口−信保额度−厂端额度）。
  - 分歧：①中信保基数（动态余额 vs 批复限额×1.5）；②维度（合同级 vs 客户级）；③816 公式展开后净占用出现两次，疑似笔误需确认本意；④计算归属（816 划给风控模块，1641 是我方接口在服务合同模块）。
  - 待拍板：以哪套为准；若 816 为准，1641 改公式（破坏性变更，已上 UAT、合同模块可能在联调，需打招呼）/场景分工/废弃。

### 7. 报表与查询（A7）

- 池台账/占用释放明细：D365 视图 + 高级查找即可满足，无需开发报表；
- 订单已发货未投保清单：数据源在上游订单/交货单 → **归属待确认**（群内确认 2 自己也标了"不确定"），若上游推数据到 CRM 则我方出视图，否则归上游。

### 8. 对外接口层（A8）

统一 Custom API 模式（同 `mcs_AdjustFcaQuotaBalance`），鉴权用 D365 Application User。建议接口清单（6 个，对应文档"6 个接口"）：

| # | API | 方向 | 用途 |
|---|---|---|---|
| 1 | `mcs_AdjustFcaQuotaBalance`（复用/轻量扩展，v2.2） | 上游→CRM | 占用/释放/重占（幂等、哑记账） |
| 2 | `mcs_QueryCreditPool` | 上游→CRM | 查池总额/余额/净占用（客户维度） |
| 3 | `mcs_CheckCreditBeforeDelivery` | 上游→CRM | 发货前校验（三档结果） |
| 4 | `mcs_JudgeOrderCreditType` | 上游→CRM | 订单授信类型判定 |
| 5 | `mcs_QueryCreditChangeDetail` | 上游→CRM | 明细查询（对账/报表） |
| 6 | `mcs_SyncSinosureQuota` | 中信保→CRM | 信保限额同步（若现有同步机制不满足时效，复用或扩展 `mcs_zxb_approvedquota` 现行同步） |

### 9. 事务/幂等/对账（A9）

- 幂等：Alternate Key + 插件查重（见 §2）；
- 事务：插件内写明细+更新余额同一事务，失败回滚（D365 天然支持，文档"与业务同事务"的说法在上游侧只能靠上游自身保证）；
- 对账：每日定时任务（Power Automate/定时插件）核对 Σ明细 vs 池余额冗余字段、快照 A/R/S 一致性，差异出清单。

### 10. 上线切换

- 期初：中信保"签约未发货"占用明细梳理 → 导入 `mcs_fca_records`（source_type=DELIVERY 期初标记）；厂端无期初（新业务，文档已确认）；
- 期初导入后核对：Σ期初明细 = 与业务确认的在途占用清单总额；
- 切换窗口：`mcs_AdjustFcaQuotaBalance` 尚未发 UAT、零调用，扩展后随下批发布即可，无切流问题。
