## 一、范围与总览

| 接口 | Custom API 唯一名 | 调用方 | 我方职责 |
|---|---|---|---|
| 使用授信 API | `mcs_recordCreditDetail` | 交货单、订单、解款记录（SAP/上游系统） | 校验入参 → 幂等保存台账 → 更新厂端余额 → 返回结果 |
| 查询授信 API | `mcs_queryCreditBalance` | 合同模块 | 客户维度授信信息查询；传合同编码时附带合同授信金额 |

**不变的原则**：
- 哑记账：金额（含 max(0, A−R−S)、ΔS）全部由调用方算好传入，我方不做计算；
- 复用 `mcs_fca_quota`（厂端额度）+ `mcs_fca_records`（台账），区别字段一律新增；
- 旧 `mcs_AdjustFcaQuotaBalance` **保留不动**（未发 UAT、零调用，看板 pending_release 维持），新接口**新建**而非扩展——参数集已明显不同（creditType/CNY/发货单/解款单），新建不影响旧契约。

**大前提（调用方保证）**：订单创建日期 ≥ 2026-09-03 且成交条件为赊销（中信保赊销/厂端授信）才调用使用授信接口。

## 二、使用授信 API（mcs_recordCreditDetail）—— 先开发

### 2.1 处理流程（PreOperation 同事务，失败整体回滚）

1. **入参校验**：
   - `mcs_accountid` 按客户主数据 `mcs_sapnumber` 匹配客户，查不到 → 失败返回；
   - `mcs_adjust` ∈ {1初始化, 3占用, 4释放}；`mcs_proccess` ∈ 1~12；
   - 条件必填：环节≥3 → `mcs_contractid` 必填；环节 6-10 → `mcs_orderid` 必填；发货/解款类事件 → 发货单号/解款单号+明细guid 必填；
   - `mcs_creditType` 选填，不传默认 **FACTORY**（与现状一致；待确认点 ①）。
2. **幂等检查**：以「单据号 + 环节 + 动作」查重 `mcs_fca_records` 新字段；命中 → 直接返回上次结果（mcs_usedflag=1 + 原台账编号），不重复记账。幂等键建议：
   - 发货类：`delivery_no + proccess + adjust`
   - 解款类：`settle_id`（解款明细 guid 天然唯一）
   - 兜底：`contractid + orderid + proccess + adjust + amount`（待确认点 ②）
3. **写台账** `mcs_fca_records`：旧字段照写（asisbalance/adjustamt/tobebalance/proccess/adjust/合同/订单 Lookup），新字段写 credit_type、CNY 金额、发货单号、解款单号、解款明细 guid、幂等键。台账编号沿用现有自动编号（FCR+YYYYMMDD+5位序列）。
4. **更新余额**：
   - creditType=FACTORY：更新 `mcs_fca_quota.mcs_usedsellerbalance`（占用金额）与 `mcs_sellerbalance`（余额，允许负数）——复用旧 API 同款逻辑，**授信额度=余额+占用** 不变式维持；
   - creditType=SINOSURE：**不建信保余额落库字段**，信保净占用由台账实时聚合（Σ占用−Σ释放，credit_type=SINOSURE）——与查询接口"使用明细快照占用数据"口径一致（待确认点 ③）。
5. **返回**：按对方表格原样回显 + usedbalance/sellerbalance/usedflag/recordid/failreason。

### 2.2 `mcs_fca_records` 新增字段（MetadataTool 公共方法创建）

| 字段 | 类型 | 说明 |
|---|---|---|
| mcs_credit_type | Picklist | 1=FACTORY 厂端 / 2=SINOSURE 中信保（旧记录为空=厂端，语义兼容） |
| mcs_usebalance_cny | Money | 占用/释放金额 CNY（对方传入快照） |
| mcs_delivery_no | Text | 发货单编码 |
| mcs_settle_no | Text | 解款单号 |
| mcs_settle_id | Text | 解款单明细 guid |
| mcs_idempotency_key | Text | 幂等键（单据号+环节+动作拼接），插件查重用 |

> 不加 Alternate Key（元数据改动重、旧记录无键值），由插件 PreOp 查重保证幂等——与旧 API 防重模式一致。

### 2.3 代码结构（复用旧 API 模式）

远程仓库 `SanyD365.D365ExtensionApi.Sales` 项目：
```
Apis/CreditPool/
  RecordCreditDetailPlugin.cs        // Custom API 绑定类（PreOp）
  Services/RecordCreditDetailService.cs  // 校验+幂等+台账+余额
```

## 三、查询授信 API（mcs_queryCreditBalance）—— 后开发

### 3.1 取数来源映射（22 个返回字段）

| 返回字段 | 取数来源 |
|---|---|
| 客户编码/合同编码 | 入参回显 |
| 授信金额 USD/CNY（传合同才查） | 合同实体 `mcs_contract` 上的授信金额字段——**字段待定**（待确认点 ④） |
| 中信保批复限额 USD | `mcs_approvedquota`：quotastate=1 + 当前在生效/失效区间，按客户（买方代码经 `mcs_sinosure_buyercode` Lookup 关联）汇总 `mcs_quotasum`；分信用证/非信用证还是全类型求和 → 待确认点 ⑤ |
| 中信保批复限额余额 USD | `mcs_approvedquota.mcs_quotabalance` 汇总（T+1 参考值，String 类型需转换） |
| 上浮限额 USD | min(批复限额 × 系数, 封顶)，系数/封顶/不适用国家走 `ms_systemconfiguration` JSON 参数化（CofaceCountryConfig 先例） |
| 中信保净占用 USD | 台账实时聚合：credit_type=SINOSURE，Σ占用 − Σ释放 |
| 上浮余额 USD | 上浮限额 − 中信保净占用 |
| 客户交易基线额度/余额 USD | `mcs_fca_quota.mcs_sellergrant` / `mcs_sellerbalance` |
| 客户风险敞口 USD | 厂端授信净占用 = `mcs_fca_quota.mcs_usedsellerbalance` |
| 客户签约占用 USD | **来源待定**（816 把计算划给合同模块；待确认点 ⑥） |
| 全部 CNY 字段 | USD × 汇率实时换算；汇率来源复用现有 `CurrencyConversionHelper`（厂端授信模型计算已用） |

## 四、与 v2.2 方案的主要改动（评审重点）

1. **接口 6 → 2**：A4 发货前校验、A5 授信类型判定、明细查询、信保同步不再是独立接口。判定/校验职责回归调用方（对方在推单前自行判断 creditType 传入）。
2. **新建 `mcs_recordCreditDetail`** 而非扩展旧 `mcs_AdjustFcaQuotaBalance`；旧 API 保留。
3. **环节枚举扩到 12**（旧 API 1-11），新增发货单/解款单参数。
4. **信保侧不落余额库**：净占用全部走台账聚合（省落库字段，避免双写不一致）。
5. **查询接口合并客户+合同维度**，中信保批复限额读 `mcs_approvedquota`（摸底结论沿用）。
6. **上浮配置参数化**：`ms_systemconfiguration` JSON（系数 1.5 / 封顶 8M / 国家清单，对方明确"动态变化"）。

### 6.1 🚨 Custom API 注册红线（#1641 幽灵 Step 事故教训，强制执行）

**事故回顾**：此前给 Custom API 绑定类注册时，`register-plugin` 命令默认实体（mcs_credit_scoringcard）副产品创建了一个实体 Step——该幽灵 Step 随 McsPlugin 发布生产时变成缺依赖项（`CalculateRiskExposurePlugin`），导致导入失败。

**本次两个 Custom API 注册时必须遵守**：
1. `mcs_recordCreditDetail` / `mcs_queryCreditBalance` 的绑定类（RecordCreditDetailPlugin / QueryCreditBalancePlugin）**只允许绑定到 Custom API 本身的消息**（sdkmessage = Custom API 的 uniquename），**严禁在任何实体消息（Create/Update 等）上注册 sdkmessageprocessingstep**；
2. 使用整改后的工具：`register-plugin` 已去默认实体、五个 Step 注册入口已拦截「Custom API 绑定类建实体 Step」，但仍需人工核对命令输出，确认没有意外创建 Step；
3. 注册完成后**必跑 `check-step-assembly`**（只读命令）复查：两个 API 的绑定类在主 Assembly 下应为 **0 条实体 Step**；同时核对 McsPlugin/McsCustomAPI 无新增跨包依赖；
4. 发 UAT/生产前，跑 `simulate_import.py` 离线导入仿真 + 上线核对清单 2.2 跨包依赖闭合校验。
