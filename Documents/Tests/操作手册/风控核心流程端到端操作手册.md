# 风控核心流程端到端操作手册（信用评估 → 厂端授信 → 额度运用）

> **适用对象**：测试人员
> **适用环境**：UAT（https://sany-uat.crm5.dynamics.com）/ DEV1
> **文档目的**：把「客户信用评估」和「厂端授信」两个模块串成一条完整链路。风控各功能数据互相关联——测厂端授信前必须先理解信用评估，否则不知道数据源头在哪里。照着本手册走一遍，即可掌握全链路。
> **推荐演示客户（UAT）**：**Kedai Kek**（客户编码 `AIN202602260000`，波兰 PL，Coface ID `icon#5415240`）——该客户已有有效信用评估结果且含 NetAssets 标签，可直接用于厂端授信演示。

## 0. 流程全景图

```
【阶段一：客户信用评估】                          【阶段二：厂端授信】

  ② 内外部数据集成(11) ──自动──► Coface同步       ⑦ 模型计算(2) ──自动──► 三因子计算

  ⑤ 审核申请(14) → BPP审批 → 审批通过(15)              mcs_fca_quota（授信额度/余额/占用）

       │ 信用分/信用等级/信用有效=是
       ▼
  ■■ 「有效信用评估结果」= 厂端授信计算的数据源头 ■■

【阶段三：额度使用与动态调整】                    【生命周期闭环】

  ⑨ 额度调整申请 mcs_fca_quotaapp                 ⑪ 信用评估 365 天自动失效
       提交BPP → 审批通过 ──自动──► 更新额度表          评估过期 → 信用有效=否
       + 台账·环节2                                    → 厂端授信回退兜底逻辑
  ⑩ 业务环节占用/释放（Custom API）
```

**核心关联**：厂端授信计算的取值，全部来自阶段一的产物（信用标签、信用分、信用有效标志）。阶段一没走完，阶段二只能走"兜底逻辑"。

## 1. 前置检查（每个环境只需确认一次）

| # | 检查项 | 位置（实体） | 检查内容 | 缺失后果 |
|---|--------|------------|---------|---------|
| 1 | 评分项目 | 风控配置 → 评分项目（`mcs_credit_items`） | 存在编码 `NetAssets`（净资产）等 25 条 | Coface 同步不生成对应标签 |
| 2 | 评分卡 | 风控配置 → 评分卡（`mcs_credit_scoringcard`） | 按客户类别 1-7 各有区间+权重配置，含 NetAssets 区间 | 信用分算不出来 / 标签不生成 |
| 3 | Coface 取数配置 | `mcs_coface_financial_indicator` | 客户国家（如 PL）有 NetAssets 的 `mcs_typevalue` 配置且启用 | 净资产取不到（会按默认名称兜底匹配，可能失败） |
| 4 | 模型参数 | 厂端授信 → 模型参数配置（`mcs_fca_mdlconfig`） | 客户分类（S/A/B/C/I/D1-D5）× 客户等级（A0-A4/ALL）有系数1/2/3、聚合方法、历史基准额度 | 模型计算报错"未找到模型参数" |
| 5 | 模型版本 | 厂端授信 → 模型版本（`mcs_fca_mdlversion`） | 存在生效中的版本（编号如 V20260701） | 计算记录无版本，历史回款范围按当前时间取 |
| 6 | 汇率 | 设置 → 货币（`transactioncurrency`） | CNY、USD 等汇率有效 | 回款折算 USD 失败按 0 处理 |

> 配置类数据由开发用工具导入（MetadataTool / CofaceConfigImporter），界面上一般只能查看。缺失时联系开发补充。

## 2. 阶段一：客户信用评估（数据源头的产生）

**菜单入口**：风控 → 信用评估记录（`mcs_credit_record`）

### 步骤 ① 新建信用评估记录

操作：新建 → 填写以下关键字段 → 保存。

| 字段 | 说明 | 示例（Kedai Kek） |
|------|------|------------------|
| 客户 | 选择测试客户 | Kedai Kek |
| 国家代码 `mcs_countrycode` | **决定用哪国的 Coface 取数配置** | PL |
| 科法斯客户代码 `mcs_cofaceid` | Coface 系统里的客户标识，格式 `icon#数字` | icon#5415240 |

> 📖 **解释**：国家代码 + Coface ID 是后面调 Coface 接口的"钥匙"。国家代码错了，即使报告里有净资产，也可能因为找不到该国的取数配置而匹配不上 NetAssets 标签。

### 步骤 ② 推进到「内外部数据集成」（状态 11）→ 自动同步 Coface

操作：BPF 阶段推进到【内外部数据集成】。

系统自动执行（`CofaceDataSyncPlugin`）：
1. 按 Coface ID 调 URBA360 接口拉取报告 JSON；
2. 按**客户国家**从 `mcs_coface_financial_indicator` 读配置，在报告资产负债表中匹配指标编码（如 NetAssets 对应该国 type.value）；无配置时按默认名称兜底（"Net Assets"/"Equity" 等）；
3. 金额按 D365 标准汇率折算为 **USD**；
4. 只把**评分卡里配置了的指标**写入客户信用标签 `mcs_customer_tag`。

**验证点**：
- 记录上 API 状态 = SUCCESS，API 消息类似「URBA360+Full Report数据集成完成，共12个指标，标签58项」；
- 相关 → 客户信用标签（`mcs_customer_tag`）中应看到一批标签，重点确认 **净资产（NetAssets）** 这条：

| 标签字段 | 含义 | Kedai Kek 实际值 |
|---------|------|-----------------|
| `mcs_itemcode` | 指标编码 | NetAssets |
| 集成值 `mcs_itemintvalue1` | Coface 报告原始值（USD） | 11,361,465.84 |
| **复核值 `mcs_itemintvalue2`** | **最终参与所有计算的值**；首次同步默认=集成值 | 11,361,465.84 |
| `mcs_active` | 是否启用 | 是 |

> 📖 **解释（关键）**：测试同学问的"净资产标签在哪配置"——它**不是配置出来的，是这一步自动同步生成的**。找不到标签时按第 5 章 FAQ 排查。
> 📖 标签同时关联了本次评估记录（`mcs_credit_record`）和客户（`mcs_accountid`）。**厂端授信计算时按客户维度取最新的启用标签，不区分是哪次评估产生的。**

### 步骤 ③ 推进到「人工复核」（状态 12）

操作：业务人员检查各标签的**复核值**，可与 Coface 报告 PDF（附件自动生成）对照修改。

> 📖 **解释**：复核值 `mcs_itemintvalue2` 修改后**不会被再次同步覆盖**（插件只在复核值为空时才默认赋集成值）。后续信用分计算、厂端授信计算全部用复核值。演示想要特定净资产数值，就在这里改。

### 步骤 ④ 推进到「信用分计算」（状态 13）→ 自动算分

系统自动执行（`CreditScoreCalculationPlugin`）：
- 按客户类别匹配评分卡（Kedai Kek：categoryId=1，老客户）；
- 每个指标取**标签复核值**，落入评分卡区间得对应权重分，求和写入 `mcs_creditscore`。

**验证点**：记录上信用分有值（如 72）。可用第 5 章的评分卡区间手算核对，例如 NetAssets=11,361,465.84 落在 [1, 3000万) 区间 → 权重 1 分。

### 步骤 ⑤ 推进到「审核申请」（状态 14）→ BPP 审批 → 「审批通过」（状态 15）

操作：提交后 BPP 系统审批；审批通过自动回调（`BppCallbackPlugin`），记录状态变 15，并**回写客户主数据**（`mcs_customermasterdata`）：

| 客户主数据字段 | 回写内容 | Kedai Kek 实际值 |
|---------------|---------|-----------------|
| `mcs_creditscore` 信用分 | 本次得分 | 72 |
| `mcs_creditgrade` 信用等级 | 得分对应等级 | A1（100000001） |
| `mcs_creditvalid` 信用有效 | = 是 | 是 |

**验证点**：打开客户 → 客户主数据，上述三个字段有值。**至此「有效信用评估结果」产生，阶段一完成。**

> 📖 **解释**：「有效信用评估结果」不是一个单独字段，而是 = 信用分>0 + 信用有效=是 + 客户有 NetAssets 标签，三者共同构成。这正是厂端授信计算的准入判断。

## 3. 阶段二：厂端授信模型计算（消费阶段一的数据）

**菜单入口**：风控 → 厂端授信管理 → 授信模型计算（`mcs_fca_proc`）

### 步骤 ⑥ 新建模型计算记录（授信校验阶段）

操作：新建 → 选择客户（客户主数据）→ 保存，进入【授信校验】阶段。

- 【不予授信】多选字段**仅此阶段可编辑**，可人工勾选场景 1（征信黑名单）/ 2（近3年≥100万实质坏账）；勾选任一场景后点【下一阶段】会被拦截，无法进入模型计算，客户主数据【不予授信客户】被回写为"是"。
- 场景 3（实质性逾期）/ 4（集团黑名单）由系统在模型计算时自动判断。

### 步骤 ⑦ 推进到「模型计算」（状态 2）→ 自动三因子计算

系统自动执行（`FcaProcCalculationPlugin`），**这是本手册最核心的取值环节**。

#### 7.1 准入判断（决定是否走兜底）

读取客户主数据 + 信用标签，三者任一不满足 → **直接取历史基准额度兜底**，不做模型计算：

| 条件 | 取值来源 |
|------|---------|
| 信用分 > 0 | 客户主数据 `mcs_creditscore`（阶段一步骤⑤回写） |
| 信用有效 = 是 | 客户主数据 `mcs_creditvalid`（阶段一步骤⑤回写） |
| NetAssets 标签存在且启用 | `mcs_customer_tag`：`mcs_accountid`=客户 且 `mcs_itemcode`="NetAssets" 且 `mcs_active`=是 |

#### 7.2 确定客户分类，读取模型参数

- **客户分类**（`CustomerCategoryService`）：按主数据字段推导——个人客户→I；代理商（类别10/30/60/90）→按经销商等级 D1-D5；KA（1/2/3）→S/A/B；其余→C。Kedai Kek（类别20）→ **C 类**。
- **客户等级**：主数据 `mcs_creditgrade`（A0-A4，空则按 ALL 兜底）。Kedai Kek → **A1**。
- **模型参数**（`mcs_fca_mdlconfig`，按 分类+等级 匹配，匹配不到再按 分类+ALL 兜底）：系数1 `mcs_adjust1`、系数2 `mcs_adjust2`、系数3 `mcs_adjust3`、聚合方法 `mcs_aggfunc`（MIN/MAX）。
- **历史基准额度**：`mcs_fca_mdlconfig` 中 该客户分类+等级ALL 的 `mcs_countryname` 字段（字段名有历史遗留，实际存基准额度 USD），与客户等级无关。

#### 7.3 三因子计算（日志第 3-6 步）

| 因子 | 公式 | 取值来源（重点） |
|------|------|----------------|
| 财务能力 | **净资产 × 系数1** | 净资产 = 客户 NetAssets 标签的**复核值** `mcs_itemintvalue2`（USD）。Kedai Kek = 11,361,465.84 |
| 历史回款能力 | **近12个月回款月均 × 系数2** | `mcs_outstanding`（月度在外货款表）该客户近 12 个月记录的 `mcs_paymentcollectioncurrentmonthrmb`，**同一月份多条记录先按月（`mcs_createon` 的 yyyy-MM）求和作为当月值**，累计后 ÷ 12，再按汇率折 USD。范围以模型版本号日期（VyyyyMMdd）向前推 12 个自然月；**无回款记录则此因子=0**（#1403 口径，2026-07-29） |
| 基准调整额度 | **历史基准额度 × 系数3** | 7.2 读取的基准额度 |
| **初始额度** | 三者取 **MIN 或 MAX**（看参数配置的聚合方法） | — |

> 📖 **解释**：聚合方法为 MIN 时，若客户没有回款数据（历史回款能力=0），初始额度必然是 0——这不是 Bug，先看该客户 `mcs_outstanding` 有没有近 12 个月数据。

#### 7.4 逾期调整（日志第 7 步）

取 `mcs_outstanding` 中该客户：最大逾期账龄 `mcs_overdurationdays`、逾期金额合计 `mcs_newoverdueamount`、在外货款余额合计 `mcs_newremainingamount`：

| 条件 | 调整 |
|------|------|
| 最大逾期账龄 < 180 天 | 不调整 |
| ≥180 天 且 逾期/余额 ≤ 20% | 额度 × 80% |
| ≥180 天 且 20% < 逾期/余额 ≤ 50% | 额度 × 50% |
| ≥180 天 且 逾期/余额 > 50% | **额度归 0（触发不予授信场景3）** |

#### 7.5 不予授信校验（日志第 7 步尾部）

系统自动判断：**场景3**（如上表最后一行）、**场景4**（主数据 `mcs_blacklist`=是）。触发任一 → 模型计算额度和调整额度**强制归 0**，回写主数据【不予授信客户】=是，并在【不予授信】字段自动勾选对应场景。

#### 7.6 结果验证

打开计算记录查看：
- **模型计算额度** `mcs_modelgrant`、**模型调整额度** `mcs_initigrant`；
- **计算日志** `mcs_doproc`（1-9 步，每步取值都写明了，核对计算以它为准），示例结构：

```
1.取得模型维度和参数：客户分类=C, 客户等级=A1, 系数1=0.30, 系数2=6.00, 系数3=1.00, 聚合方法=MIN, 历史基准额度(USD)=500000.00
2.客户信用评估有效，继续以下模型计算过程
3.计算财务能力=净资产 x 系数1 = 11361465.84 x 0.30 = 3408439.75
4.计算历史回款能力=近12个月客户回款月均值 x 系数2 = ...
5.调节历史基准额度=历史基准额度 x 系数3 = ...
6.取三者【MIN】值作为厂端授信【模型计算额度】的初始额度=...
7.取值客户逾期账龄=0天, 逾期金额/在外货款余额=0.00%... 不做调整
8.计算厂端授信结束
9.计算时间：...
```
（日志中数值为示意，以实际为准；若第 2 步显示"采用历史基准额度兜底"，回到 7.1 逐条排查。）

### 步骤 ⑧ 推进到「生效启用」（状态 3）→ 自动写额度表

系统自动执行（`FcaProcActivationPlugin`）：
1. 在**厂端授信额度表**（`mcs_fca_quota`）创建/更新该客户额度：授信额度 `mcs_sellergrant` = 模型调整额度，**授信余额 = 授信额度 − 已占用**（不变式：额度 = 余额 + 占用），生效状态=是；
2. 在**台账表**（`mcs_fca_records`）生成一条"环节1-厂端授信模型计算 / 初始化"记录。

**验证点**：额度表有该客户记录且额度与计算记录一致；台账有一条初始化记录。全链路完成 ✅

## 4. 阶段三：额度的使用与动态调整

阶段二【生效启用】只是让客户“有了额度”。额度后续怎么变，由本章两个功能驱动。

### 步骤 ⑨ 额度调整申请（`mcs_fca_quotaapp`）→ BPP 审批

**菜单入口**：风控 → 厂端授信管理 → 厂端授信额度调整申请。

适用场景：模型算出的额度不够用（或需要调减/归零），业务发起人工调整。

操作：新建 → 选客户（自动带出当前额度/占用/余额）→ 填【调整后额度】和调整原因 → 保存 → 点【提交】送 BPP 审批。

系统自动执行：
1. 提交后表单**全字段只读**（审批中/审批通过都锁定，驳回/撤回后可改再提交）；
2. BPP 审批通过自动回调（`FcaQuotaAppBppCallbackPlugin`），更新额度表：
   - 授信额度 = 调整后额度；
   - **授信余额 = 调整后额度 − 当前占用金额**（服务端实时重算，不信前端传入的余额）；
   - 归零场景：余额 = −占用（负余额保留敞口，后续回款释放可加回）；
3. 台账表写入一条 **环节2（厂端授信限额额度申请）** 记录。

**验证点**：审批通过后额度表的额度/余额已更新；台账有环节2记录。

> 📖 **解释**：申请单上的【调整后余额】只是提交时的参考快照，最终以服务端「额度−占用」重算为准——防止审批期间占用发生变化导致余额失真。

### 步骤 ⑩ 业务环节的占用与释放（Custom API `mcs_AdjustFcaQuotaBalance`）

这不是测试人员在界面上操作的功能，而是**供合同/订单/回款等业务环节调用的统一内部接口**。测试人员需要理解它，因为额度表的余额变化全部来自这里。

**核心不变式（牢记）**：**授信额度 = 授信余额 + 占用金额**。占用增加→余额减少；释放→余额回升；余额允许为负（超额不拦截，表示敞口）。

**动作与允许环节**：

| 动作 | 允许环节 | 典型业务场景 |
|------|---------|-------------|
| 1 初始化 | 1 模型计算 / 2 额度调整申请 | 由阶段二步骤⑧/步骤⑨自动完成，无需手工调 |
| 3 占用 | 6 订单执行验收（发货） | 发货时占用额度 |
| 4 释放 | 5 合同取消 / 7 订单变更信用类别 / 8 回款解款 / 9 订单退货 / 10 订单取消 | 钱回来了或交易取消了，额度释放 |

关键规则：
- **占用防重**：同一客户 + 同一订单号（无订单号则用合同号）只能占用一次，重复占用被拦截；释放不防重；
- **条件必填**：环节 ≥3 必须传合同编码；环节 6-10 必须传订单编码；
- 每次调用成功都在台账表写一条记录（环节=入参环节，动作=占用/释放），逐笔可追溯。

**测试方法**：由开发用工具命令 `test-fcaquota-api <客户编码> <金额> <环节> <动作> [合同编码] [订单编码]` 直接调用验证，或在业务模块触发真实环节。

**验证点**：额度表【占用金额】【授信余额】随之变化且满足不变式；台账逐笔留痕。

## 5. 生命周期闭环：信用评估 365 天自动失效

**功能**：信用评估审批通过后有有效期（365 天）。过期处理由 `CreditRecordExpiration` 服务任务完成（当前为手动执行的工具，后续配置定时任务）：

1. 扫描【审批通过日期】距今超过 365 天且仍启用的评估记录 → 置为不启用；
2. 检查该客户是否还有其他未过期的有效评估记录，**没有则把客户主数据【信用有效】置为“否”**。

**为什么影响大流程**：信用有效=否后，阶段二准入判断（见 3.1 节）不通过 → 新的模型计算**回退历史基准额度兜底**。所以“客户以前评估有效、突然算出来是基准额度”，先查评估是不是过期了。

**测试方法**：由开发造一条审批通过日期超过 365 天的评估记录并执行失效任务，验证：评估记录不再启用 + 主数据信用有效=否 + 重新模型计算走兜底逻辑。

## 8. FAQ（排查速查）

**Q1：Coface 同步成功但客户没有 NetAssets 标签？**
按顺序查：① 评分卡是否配置了 NetAssets（没配置的指标不生成标签）；② `mcs_coface_financial_indicator` 中该客户国家是否有 NetAssets 配置且启用；③ 该国 Coface 报告是否真含资产负债表（小国客户可能只有评级无财报）；④ API 消息里的指标/标签数量是否正常。

**Q2：厂端授信计算结果直接等于历史基准额度（日志第 2 步"兜底"）？**
三条件缺一：主数据信用分=0 / 信用有效≠是 / 无启用的 NetAssets 标签。最常见是阶段一没走完 BPP 审批（状态没到 15），主数据没回写。

**Q3：初始额度 = 0？**
聚合方法=MIN 且客户近 12 个月无 `mcs_outstanding` 回款记录 → 历史回款能力=0 → MIN 后=0。补回款数据或将聚合方法改 MAX（需业务确认）。

**Q4：额度被归 0 且提示不予授信？**
看日志第 7 步：要么逾期触发场景3（账龄≥180天且逾期占比>50%），要么客户被标黑名单（场景4），要么授信校验阶段人工勾选了场景。

**Q5：想改演示用的净资产值？**
改客户信用标签 NetAssets 的**复核值**（`mcs_itemintvalue2`），改集成值没用——计算只取复核值。改完重新发起模型计算即可（再次同步 Coface 不会覆盖复核值）。

**Q6：模型计算能重复跑吗？**
可以。把计算状态从其他状态再次改为 2（如退回后重新推进 BPF）会重新计算；状态已是 2 时重复保存不会重复触发。

**Q7：额度调整申请审批通过了，但额度表余额和申请单上对不上？**
正常。审批通过时服务端按「调整后额度 − 实时占用」重算余额，申请单上的调整后余额只是提交时的快照。以额度表和台账（环节2）的服务端结果为准。

**Q8：额度表【授信余额】为什么是负数？**
两种可能：① 占用超过了额度（超额不拦截，负余额=敞口）；② 额度调整归零时按「0 − 占用」保留负余额，等回款释放逐步加回。符合「额度=余额+占用」不变式即正常。

**Q9：发货环节占用额度报重复？**
占用按「客户 + 订单号（无则合同号）」防重，同一单据只能占用一次。检查是否重复调用，或上一笔占用尚未经取消/退货/回款环节释放。

**Q10：客户之前信用评估是有效的，突然模型计算走兜底了？**
大概率是评估记录审批通过已满 365 天被失效任务置为不启用，且客户无其他有效评估 → 主数据信用有效被置否。检查评估记录的审批通过日期和启用状态，需要时重新发起评估。

## 附录 B：状态值速查

**信用评估记录 `mcs_credit_record.mcs_status`**：11=内外部数据集成（Coface 同步）→ 12=人工复核 → 13=信用分计算（自动算分）→ 14=审核申请（提交 BPP）→ 15=审批通过（回写主数据）。

**厂端授信模型计算 `mcs_fca_proc.mcs_status`**：1=授信校验 → 2=模型计算（触发三因子计算）→ 3=生效启用（写额度表+台账）。

**额度调整申请 `mcs_fca_quotaapp.mcs_bppstatus`**：1=申请 → 2=审批中（表单只读）→ 3=通过（触发额度表更新）/ 4=驳回（可编辑重提）。

**台账 `mcs_fca_records.mcs_proccess` 环节值**：1=模型计算、2=额度调整申请、5=合同取消、6=订单发货（占用）、7=订单变更信用类别、8=回款解款、9=订单退货、10=订单取消、11=其他。
